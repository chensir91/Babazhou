================================================================================
一、项目概述
================================================================================
八宝舟是一款双人回合制战棋策略对战游戏，在7×5棋盘上进行。双方各选5名角色(从24名角色池中Ban/Pick)，通过布阵、选位、行动等阶段展开对战。纯前端单文件实现(HTML+CSS+JS)，部署于GitHub Pages，面向手机端浏览器。

技术栈：纯原生JavaScript + CSS Grid布局，无框架依赖。

================================================================================
二、已实现功能清单
================================================================================

【核心对战流程】(全部已实现)
- BAN阶段：双方交替禁用4个角色(1-2-2-1顺位)，24角色chip网格展示，蓝/红/黑边框+斜线区分状态
- PICK阶段：10轮交替选人(1-2-2-1-1-2-2-1-1-2顺位)，已选角色灰显不可重复选取
- 布阵阶段(Deploy)：拖放角色至己方区域(x=0~2为蓝方,x=4~6为红方)，x=3中线禁止放置
- 选位阶段(Reposition)：每大回合开始前交替调整站位。支持地图点击选中角色挪位、点击空格放置、点击同一角色取消选中
- 行动阶段：先手方全部单位行动完毕后切换后手方，双方都行动完进入下一大回合
- 先手判定：总敏捷→总HP上限(低者先)→总ATK(高者先)三级比较

【战斗系统】(全部已实现)
- 伤害计算：伤害=ATK×倍率，向下取整；护盾优先扣除；穿透无视护盾
- 普攻/技能/大招三级行动体系
- 技能冷却(CD)系统：每个小回合(敌我双方)CD-1，归零后存储+1
- 大招充能(Charge)系统：自充(大回合+1)/攻充(命中+1)/受充(受击+1)
- 大招持续(ultDur)机制：持续期间无法使用技能、不获得充能
- 自动大招(auto=1)：充能满后小回合结束自动触发，多单位按敏捷降序结算
- 冲锋(charger)机制：攻击范围变身前整行，无单位则扩至三行
- 冷场(triggerColdField)：击杀敌方后全场普攻触发

【异常状态系统】(部分已实现)
- 恐惧(fear)：叠至10触发4点伤害
- 眩晕(st)：跳过回合，敌方可无视攻击逻辑
- 束缚(bd)：无法移动
- 流血(bl)：每大回合开始扣2HP
- 隐匿(sth)：无法被单体选中，群伤仍有效
- 无敌(inv)：免疫伤害
- 嘲讽(taunt)：只能普攻嘲讽来源
- 蓄力(chging)：下回合释放强化攻击
- 损伤叠层(ailment)：fear/neuro/burn分别累计

【召唤物系统】(全部已实现)
- 毛毛虫(陈色)：HP1，受虫迷加成，冷8存4
- 大树(松龄)：HP99，每回合治疗周围队友2HP
- 老鼠(加州老鼠)：HP1,ATK1，最多6只
- 雪豹(丁衍征一)：HP4,ATK0
- 召唤物isS=true，不可选中/操控，不参与选位

【UI系统】(全部已实现)
- 手机端适配：max-width:375px，棋盘368px(9×5格,每格40px+1px间隙)
- CSS Grid 9×5棋盘布局，单位grid-column/grid-row自动对齐
- 棋盘背景渐变：蓝方区域(深蓝)/中线(透明)/红方区域(深红)
- BAN/PICK：24角色chip网格，蓝/红/黑/灰四色状态
- 侧栏系统：42×42正方格角色列，蓝红渐变区分阵营
- 战斗日志：📋按钮弹窗，按回合分组section，按阶段分条
- 改动日志：左下角📝按钮弹窗
- 版本号：右上角badge
- 技能面板：当前选中单位技能列表，可点击释放

【开发者模式】(全部已实现)
- Dev模式：蓝方1角色 vs 红方人机(HP10/ATK1/AGI0)
- 拖动人机调整位置
- "+人机"按钮在空格新增人机
- "全体冷却-1"/"全体充能+1"调试按钮

三、曾经遇到的问题及解决方案
================================================================================

1. 棋盘布局适配问题(多次)
   问题：手机端棋盘在重构过程中多次出现单位未对齐、棋盘溢出、偏移等问题
   解决：最终采用width:368px+margin:auto居中方案，grid-template-columns:repeat(9,40px)，单位用grid-column/grid-row定位。关键是在容器上去掉justify-content:center改用margin:auto

2. 选位阶段角色重复显示(v1.67-v1.72,多轮迭代)
   问题：选位阶段角色同时出现在地图和侧栏，或在两个棋盘同时出现；_repoPlaced初始化时机和内容错误
   解决历程：尝试过_repoPlaced初始化为空Set→地图只显示已放置角色(仍有bug)→最终方案：_repoPlaced初始化为全部单位UID，地图显示所有角色，通过地图点击实现选中挪位。关键是把_repoPlaced初始化放到单位全部创建之后

3. v1.57棋盘统一重构导致大量代码丢失(v1.62-v1.64)
   问题：将三阶段棋盘统一为9×5 CSS Grid时，误删了大量核心战斗函数和UI函数
   丢失函数：getChargeTarget/triggerColdField/isChargeUnit/getChargeRows/onBClick/doAction/finishAction等等
   解决：分多次补回，v1.63补核心战斗函数，v1.64补toggleDummyMove/toggleAddDummy

4. isRepo变量未前置声明(v1.62)
   问题：isRepo变量在渲染循环中首次使用但未用let/var声明，导致地图空白
   解决：在函数顶部添加let isRepo前置声明

5. ROSTER数据丢失(v1.57后→v1.73回退)
   问题：棋盘重构时将24角色ROSTER缩减为仅剩陈色和周水2个角色(其余角色的技能代码和被动描述全部丢失)
   解决：从Git历史v1.56的Babazhou_full.html恢复完整24角色数据，回退至重构前版本

6. GitHub Pages文件命名问题
   问题：Babazhou_full.html和index.html不同步，GitHub Pages只serve index.html
   解决：统一使用index.html作为部署文件，full版本仅作备份

7. 瞬杀时刻描述与实际代码不一致
   问题：周水大招描述写(基础攻击力+已损失生命值)*1，代码实际×2
   解决：修正描述为×2以匹配代码实现

8. ROSTER变量赋值丢失等号
   问题：精简ROSTER时切割字符串偏移错误，导致"const ROSTER=["变成"const ROSTER["
   解决：字符串替换修复

六、项目心得
================================================================================

【技术架构方面】
1. 单文件架构的利与弊：单文件index.html(~80KB)部署极其方便(GitHub Pages直接serve)，但随着功能增长，代码导航和维护越来越困难。24个角色的ROSTER数据与战斗逻辑混在一起，改一个技能可能要在几万行中定位。

2. CSS Grid的坑：9×5 Grid布局在手机端非常敏感，width:368px是经过多次试错得出的精确值(=9格×40px+8间隙×1px)。任何对gap/width/padding的改动都可能导致棋盘溢出。margin:auto比justify-content:center在窄屏上更可靠。

3. 没有框架的代价：纯原生JS虽然零依赖，但状态管理(全局b对象)、DOM操作(大量getElementById/querySelector)和事件绑定全部手工管理。随着24个角色和多种阶段的增加，视图更新逻辑中充满了if-else分支，容易出现"改A坏B"的问题。

【开发流程方面】
4. 版本管理的重要性：v1.57棋盘重构是最大教训——一次"为了统一"的重构删除了大量核心代码，导致后续6-7个版本都在补洞。如果重构前做了完整备份和功能清单对照，可以避免这个灾难。Git的版本回退能力救了这个项目。

5. 手机端测试的必要性：用户全程在手机端测试，而开发在桌面端。多次出现"桌面正常、手机炸裂"的情况(如棋盘溢出、pointer-events问题)。每次提交后应立即在手机上验证。

6. 用户反馈与迭代：用户对bug的描述风格是直接描述现象("悬浮的地图"、"角色重复")，而非技术术语。需要按字面含义排查(如检查是否有叠加DOM)，而非自行推断间接原因。用户对"过度分析"不耐烦，偏好直接修复。

【游戏设计方面】
7. 规则与实现的鸿沟：原版规则书极其详尽(九章)，但代码实现只能覆盖一部分。24个角色各有特色机制(召唤/电荷/形态切换/怒气等)，每个都需要独立的代码逻辑。需要有策略地选择先实现核心机制还是追求完整性。

8. 角色平衡的敏感性：用户对角色描述极其在意("少了个QC"、"改的有点狗屎了")。角色数据是游戏的灵魂，任何删改都必须经过用户确认。

9. 从"能跑"到"好用"：BAN/PICK/布阵/战斗框架搭好后，大量的工作在于UI细节——侧栏显示规则、选中高亮、日志分组、异常状态提示等。这些细节决定了实际游戏体验。

【个人反思】
10. 这个项目展现了一个经典的单人全栈游戏开发过程：从一套规则书出发，逐步实现核心循环，在迭代中踩坑、回退、修复。最大的教训是——不要为了"代码整洁"而大规模重构已有的工作代码。增量修改、保留备份、频繁提交才是稳健策略。
